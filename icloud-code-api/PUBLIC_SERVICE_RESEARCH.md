# 公开服务调研结论

调研时间：2026-08-05

## 结论

1. 没有找到 Apple 官方面向第三方开放的“读取 iCloud Mail 验证码/最新邮件”通用托管 API。Apple 官方入口是 `icloud.com`、`icloud.com.cn` 及 `apple.com` 体系；这类服务需要通过用户授权的 iCloud Mail/IMAP 能力实现，不能把第三方站点当作 Apple 官方 API。
2. 用户提供的两个示例站点属于独立第三方域名。它们的页面形态是“邮箱标识 + 随机访问令牌 + 最新邮件查看页/JSON”，域名本身不能证明与 Apple 官方有关，也不应复用其访问令牌或直接复制其凭据传递方式。
3. `icloud-api.top` 等第三方服务不是 Apple 官方服务。正式商业化接入前应做域名、隐私政策、数据保留、授权来源和服务条款审查；本项目不依赖这些站点。

## 本项目采取的实现边界

- 仅使用客户自行生成的 iCloud App 专用密码连接 `imap.mail.me.com`；不收集 Apple ID 主密码、Cookie、CK 或浏览器会话。
- 客户访问取码接口使用 `X-Mailbox-Key` 请求头；邮箱地址不放进客户 API URL。
- 公开查看页使用独立随机不透明令牌，不把邮箱地址或邮箱 API Key 放进 URL；令牌只显示一次，可轮换和撤销。
- 邮件同步后提取验证码，客户接口只返回最新验证码及有限邮件元数据；启用 R2 时原始 MIME 仅归档到私有 bucket，客户接口不提供对象直读。
- Cloudflare R2 只通过环境变量预留，任何真实 Token/Access Key/Secret 都不写入代码、示例文件、数据库初始化脚本或日志。

## 参考页面与本项目的差异

参考页面提供了“最新邮件、验证码、自动刷新、公开查看”的交互思路，本项目保留这些产品层能力，但把鉴权改为租户隔离、每邮箱 Key 和可撤销的 opaque public token，减少邮箱地址和凭据出现在 URL、历史记录及反向代理日志中的机会。
